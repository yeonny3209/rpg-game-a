# 기술 설계 개요

작성: 2026-11-05 · 리드 개발: Claude · 기준 문서: 기획서 1~5권, [결정기록.md](결정기록.md)

5권 11장 제안은 참고만 했고, 아래가 최종 결정이다. 바꿀 때는 이 문서를 고치고 이유를 남긴다.

## 0. 한눈에 보기

```
[브라우저: Unity WebGL 클라이언트]
     │  WebSocket (바이너리, 개발 ws:// / 배포 wss://)
     ▼
[게임 서버: .NET 8 C# 콘솔 앱]  ← data/*.json (데이터 테이블)
  ├ Gateway: 접속·인증·세션
  ├ World: 지역(Zone) × 채널 인스턴스, 각자 20Hz 틱
  └ 전역 서비스: 유일한 자리 / 거래 / 경매 / 우편 / 강화·진화
     │  Npgsql + Dapper
     ▼
[PostgreSQL 16]  계정·캐릭터·아이템·경매·길드·유일한 자리·감사 로그

[Game.Shared]  프로토콜·데이터 스키마·전투 공식 → 서버와 Unity가 같은 C# 소스를 씀
```

| 영역 | 결정 | 한 줄 이유 |
|------|------|-----------|
| 클라이언트 | Unity 6 LTS, **URP**, WebGL 2 | HDRP는 WebGL 미지원. URP가 내장 그래픽에서 가장 가벼움 |
| 서버 | **.NET 8 전용 C# 서버** (Unity 헤드리스 아님) | 가볍고 빠르고, 기획자 PC·무료 리눅스 서버(Oracle 무료 ARM) 어디서든 돌아감. C#이라 클라와 코드 공유 |
| 통신 | **WebSocket + 자체 바이너리 프로토콜** | WebGL은 UDP 불가. 의존성 없는 직렬화라 IL2CPP·WebGL에서 안전 |
| DB | **PostgreSQL 16** (무료, 관리자 권한 없이 사용자 폴더에 설치). Redis는 쓰지 않음 | 유일한 자리 잠금을 DB 트랜잭션으로 보장. 5권 11.1(개정)의 'SQLite로 시작' 제안 대신 PostgreSQL을 유지: 비용 0원 조건을 똑같이 지키고, 이미 설치·검증됨. DB 계층은 `ICharacterStore`로 분리돼 있어 SQLite로 바꾸는 것도 가능 |
| 데이터 | **JSON 데이터 테이블** (공용 / 서버 전용 분리) | 서버(.NET)와 클라 둘 다 읽음. 사람이 읽고 diff 가능 |

## 1. 클라이언트 (Unity WebGL)

### 1.1 엔진 설정
- **Unity 6 LTS** (설치할 때 Hub에서 최신 LTS 버전을 골라 `ProjectVersion.txt`로 고정)
- **URP**, Linear 색공간, WebGL 2.0, IL2CPP, 압축 Brotli(배포) / 개발 중엔 Decompression Fallback
- **Input System** (키 재배치가 확정 기능이라 처음부터 액션 맵으로 작성)
- **Cinemachine 3** (3인칭 뒷시점 → 나중에 쿼터뷰 카메라를 하나 더 추가해 설정에서 전환)
- **Addressables**: 지역 씬, 캐릭터·몬스터 프리팹, 이펙트를 그룹 단위로 필요할 때만 로드

### 1.2 성능 전략 (1권 4.2 준수)
| 항목 | 낮음 | 중간 | 높음 |
|------|------|------|------|
| 렌더 스케일 | 0.6 | 0.8 | 1.0 |
| 그림자 | 없음 또는 1캐스케이드 20m | 1캐스케이드 40m | 2캐스케이드 80m |
| 후처리 | 없음 | 톤매핑만 | 톤매핑 + 블룸 |
| 다른 플레이어 상세 표시 | 10명 | 20명 | 40명 (나머지는 단순 모델) |
| 목표 | **Iris Xe 30fps** | — | — |

- **2560×1600 화면 주의**: 브라우저의 devicePixelRatio 때문에 실제 렌더 해상도가 아주 커질 수 있다. WebGL 템플릿에서 DPR 상한(낮음 1.0)을 걸고 렌더 스케일과 함께 조절한다. 내장 그래픽에서 프레임에 가장 크게 영향을 준다.
- 라이트는 베이크 위주, 실시간 라이트는 해 1개. LOD 그룹, GPU 인스턴싱, 텍스처는 ASTC/DXT 압축.
- 한 번에 한 지역만 메모리에 올리고, 지역을 옮길 때 짧은 로딩 화면을 보여 준다.
- FPS 오버레이: FPS, 프레임 시간(ms), 핑, 접속 인원. 단계 0부터 항상 켤 수 있게(F11 토글 예정).

### 1.3 클라이언트 코드 구조
- `Boot` 씬 → 설정·데이터 로드 → `Login`(닉네임) → 지역 씬(Addressables)
- 네트워크 엔티티는 서버가 준 `EntityId`로 관리하고, 원격 엔티티는 **100ms 지연 보간**으로 부드럽게 보여 준다.
- 내 캐릭터는 **클라이언트 예측**으로 바로 움직이고, 서버 보정이 오면 맞춘다(2장).
- WebSocket: 에디터·PC에서는 `System.Net.WebSockets`, WebGL에서는 `.jslib` 브리지. 같은 인터페이스(`ITransport`)로 감싼다.

## 2. 게임 서버 (.NET 8)

### 2.1 왜 Unity 헤드리스 서버가 아닌가
| | .NET 전용 서버 (선택) | Unity 헤드리스 |
|--|--|--|
| PC 부담 | 가벼움(수십 MB) | 무거움. 에디터 + 서버 빌드를 같이 돌리면 16GB가 빠듯함 |
| 반복 속도 | 저장 후 몇 초 만에 재시작 | 빌드마다 수 분 |
| 물리·충돌 | 직접 구현해야 함 (아래 대응) | 공짜 |
| 규모 | 지인 30~50명은 프로세스 1개로 충분 | — |

물리가 없는 단점은 이렇게 메운다. MMO 서버에는 정밀한 물리가 필요 없다.
- 전투 판정은 **단순 도형**(캡슐, 부채꼴, 원, 직선)으로 서버가 계산한다. 후방 120° 판정도 각도 계산이면 충분하다.
- 지형은 Unity에서 **높이맵·이동 가능 영역**을 export해서 서버가 이동을 검증하는 데 쓴다(단계 1부터).

### 2.2 이동과 판정의 권한 모델
기획서의 "서버 권위 + 클라 예측"과 "이동 속도·쿨타임·데미지는 서버가 검증"(5권 11.2)을 이렇게 나눈다.

| 대상 | 방식 |
|------|------|
| **이동** | 클라가 예측해서 움직이고 위치·상태를 초당 20회 보냄 → 서버가 **최대 속도(대시·활공 포함), 점프 높이, 쿨타임, 지형**을 검증 → 어긋나면 서버 위치로 되돌림(보정) |
| **전투·드롭·퀘스트·거래·경매·강화·진화·계약** | **100% 서버가 결정**. 클라는 "공격 버튼 눌렀음 + 조준 방향"만 보내고, 맞았는지·피해·드롭은 서버가 계산해서 알려 줌 |
| 표시 | 클라는 내 공격 모션·이펙트를 바로 재생(예측)하고, 데미지 숫자는 서버 결과가 오면 표시 |

### 2.3 서버 내부 구조
- **ZoneInstance** = 지역 1개 × 채널 1개. 각자 하나의 스레드에서 **20Hz 틱**을 돌린다(락 없이 단일 스레드라 버그가 적음). 메시지는 큐로 받는다.
- 관심 영역(AOI): 지역을 격자로 나누고 주변 칸의 엔티티만 보낸다. 50명이 한 지역에 모일 때 대역폭을 줄이는 핵심.
- **전역 서비스**(지역과 무관): `UniqueSlotService`(드래곤·공허), `TradeService`, `AuctionService`, `MailService`, `EnhanceService`. 지금은 같은 프로세스 안의 클래스지만, **인터페이스로만 호출**해서 나중에 별도 프로세스로 떼어 낼 수 있게 한다.
- **규모(5권 11 개정)**: 지인 전용 30~50명, 공개 서비스 없음 → 서버 프로세스 1개. 지역·채널은 코드 안의 구조(Zone)로만 나누고, 프로세스 분리는 필요해질 때 한다.

### 2.4 나중 기능을 위해 처음부터 넣어 두는 구조 (작업 원칙 4)
| 나중 기능 | 지금 해 두는 것 |
|----------|----------------|
| 직업 변경·히든 전직 | 캐릭터의 `JobId`·`JobTier`·직업 고유 성장(훈련량·서클·신성력…)을 **별도 테이블**로 분리 → 전직 = 고유 성장 행 삭제 + JobId 변경 |
| 용기사 유지 조건 | 캐릭터에 `last_login_at`, `last_level_up_at`, `last_quest_done_at`을 단계 1부터 기록 (서버 시간 기준) |
| 유일한 자리 | 2.5의 DB 잠금 설계 |
| 채널 | ZoneInstance 키 = (지역Id, 채널번호). 단계 0은 채널 1개 |
| 파티(6)·레이드 그룹(8) | `Group` 개념 하나로 만들고 최대 인원만 데이터로 다르게 |
| 캐릭터 3슬롯 | DB는 처음부터 계정 → 캐릭터(1:N) |

### 2.5 유일한 자리 잠금 (드래곤 계약, 공허의 힘, 시련 선점)
- 테이블 `unique_slots(slot_id PK, state, holder_character_id, reserved_until, version)`.
- 선점과 계약은 **조건부 UPDATE 한 문장**으로 처리한다. 예: `UPDATE unique_slots SET holder=@me, state='trial' WHERE slot_id=@id AND state='free'` → 바뀐 행이 1이면 성공, 0이면 이미 누가 가짐. PostgreSQL이 행 단위로 원자성을 보장하므로 서버 프로세스가 여러 개가 되어도 두 명이 동시에 얻을 수 없다.
- 캐릭터별 영구 불가는 `character_slot_bans(character_id, slot_id)` + 유니크 제약.
- 동시성 테스트: 스레드 100개가 같은 자리를 동시에 요청 → 성공 1개 검증(단계 6 완료 기준, 자동 테스트로 상시 실행).

### 2.6 감사 로그
거래·경매·강화·진화·드롭(희귀 이상)·계약은 전부 `audit_log`에 남긴다(5권 11.2). 골드 생성·소멸량 집계도 여기서 계산한다(4권 3.8).

## 3. 통신 프로토콜

- WebSocket 바이너리 프레임: `[u16 메시지Id][페이로드]`.
- 직렬화: `Game.Shared`의 `NetWriter`/`NetReader`로 각 메시지가 직접 쓰고 읽는다. 외부 라이브러리가 없어서 IL2CPP·WebGL에서 리플렉션·AOT 문제가 생기지 않는다. 위치는 cm 단위 정수, 회전은 u16으로 양자화해서 대역폭을 아낀다.
- 접속 시 `Hello(프로토콜 버전, 데이터 버전)` → 서버와 다르면 "새로고침 필요"를 안내한다.
- 시간 동기화: 주기적인 ping으로 서버 시간 오프셋을 계산한다(쿨타임 표시·보간에 사용).
- 주요 메시지(단계 0): `Hello`, `Welcome`, `MoveState`(C→S), `Snapshot`(S→C), `EntitySpawn`/`EntityDespawn`, `PositionCorrection`, `Ping`/`Pong`.

## 4. 데이터베이스

- **PostgreSQL 16**: 윈도우에 설치형으로(서비스 메모리 수백 MB). Docker Desktop은 16GB PC에 부담이 커서 쓰지 않는다.
- 접근: **Npgsql + Dapper**(SQL을 직접 써서 잠금·트랜잭션이 눈에 보이게). 마이그레이션은 `server/migrations/0001_*.sql` 순번 파일을 서버 시작 때 자동 적용.
- 저장 주기: 위치는 30초마다 + 로그아웃 때. 아이템·골드·퀘스트는 **바뀌는 즉시 트랜잭션으로** 저장(서버가 죽어도 거래가 반만 되는 일 없음).
- 단계 0~1 테이블: `accounts`, `characters`, `character_stats`, `inventory_items`, `equipment`, `quest_progress`, `unique_slots`(빈 채로), `audit_log`.

## 5. 데이터 테이블

### 5.1 원칙
- [수치]와 콘텐츠 정의는 전부 `data/` 아래 **JSON 파일**. 코드에는 숫자를 넣지 않는다.
- **공용(`data/shared`)과 서버 전용(`data/server`)을 분리한다.** 히든 직업·히든 스킬 조건, 드롭률, 스폰 정보, 강화·진화 확률이 클라 빌드에 들어가면 데이터마이닝으로 비밀이 다 드러난다(디자인 기둥 2 "숨겨진 것을 찾는 탐험"). 서버 전용 파일은 절대 클라로 보내지 않는다.
- ID는 사람이 읽을 수 있는 문자열(`item.wooden_club`, `mon.rabbit`). 로드할 때 정수로 바꿔 쓴다.
- 서버가 시작할 때 **검증기**가 돌면서 참조 오류(없는 아이템 ID), 범위 오류(확률 > 100%)를 잡고, 오류가 있으면 시작을 거부한다.
- 핫 리로드: 개발 모드에서 `/reload` 명령으로 서버를 재시작하지 않고 수치를 바꿔 볼 수 있게 한다.

### 5.2 테이블 목록
| 파일 | 위치 | 내용 | 처음 쓰는 단계 |
|------|------|------|---------------|
| `game_config.json` | shared | 이동(속도·점프·더블점프·대시 쿨 2초·활공), 리스폰, 부활, 인벤토리 칸 수 등 전역 수치 | 0 |
| `exp_table.json` | shared | 2권 1.3 레벨별 필요 경험치, 레벨 차 10 이상 패널티 10% | 1 |
| `stats.json` | shared | 시작 스탯 10, 레벨당 5, 전직 +10, 스탯 효과, 전투 스탯 기본값·상한 | 1 |
| `items.json` | shared | 아이템 정의(이름, 종류, 슬롯, 등급, 직업 제한, 기본 능력치, 겹치기 999) | 1 |

| `classes.json`, `skills.json` | shared | 직업·스킬 정의, 숙련도 표 | 2 |
| `grades.json`, `enhance.json`, `evolution.json`, `random_options.json` | server (표시용 일부는 shared) | 4권 2장 | 3 |

| `hidden_jobs.json`, `hidden_skills.json` | **server** | 해금 조건 | 5~6 |

### 5.3 편집 방식
- 지금은 JSON을 직접 편집한다(VS Code에서 스키마 자동완성이 되게 `data/schema/*.json` 제공).
- 표가 커지는 단계 3쯤에 **스프레드시트(CSV) → JSON 변환 도구**를 추가할지 다시 물어볼게. 기획자가 엑셀처럼 수치를 만지는 게 편할 수 있어서.
- 클라는 공용 JSON을 빌드에 포함하지만, **최종 판정 수치는 항상 서버 값이 이긴다**.

## 6. 프로젝트 폴더 구조

```
rpg-game-a/
├─ client/                    Unity 프로젝트
```

## 7. 개발·테스트 도구

- **BotClient**: 콘솔에서 가짜 플레이어 3명을 붙여 돌아다니게 한다 → 지인이 없어도 "2~4명이 보인다"를 혼자 확인할 수 있다. 단계 9에서는 그대로 50명 부하 테스트 도구가 된다.
- **로컬 실행 스크립트**: `tools/run-local` 하나로 서버 실행 + WebGL 빌드 결과를 로컬 웹서버로 띄운다.
- **개발자 명령**(개발 모드만): `/tp`, `/level`, `/give`, `/kill`, `/reload`.
- **배포(비용 0원, 1권·5권 개정 확정)**: 기획자 PC에서 서버를 켜고 **Cloudflare Tunnel(무료)**로 외부에 연다. 게임 서버가 WebGL 파일도 같은 주소로 내보내므로 Cloudflare Pages의 파일당 25MiB 한도와 상관없다(터널로 직접 전달). 터널이 큰 파일·WebSocket을 문제없이 넘기는지는 첫 원격 테스트 전에 실제로 확인한다. 24시간 서버가 필요해지면 Oracle Cloud 무료 ARM을 검토한다(한도·과금 조건은 그때 공식 문서로 확인).
